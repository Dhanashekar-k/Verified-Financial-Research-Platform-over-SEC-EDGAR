## ADR-001: Iceberg lake is the source of truth; Postgres is a rebuildable serving copy (2026-11-16)
**Status:** accepted
**Context:** Heavy batch processing (all XBRL facts since 2009, parsing and embedding about a million chunks) needs cheap storage and distributed compute. Interactive questions need tens-of-milliseconds lookups. Athena takes seconds and charges per scan.
**Options considered:** (a) everything in Postgres: simple, but no lake semantics and painful full rebuilds; (b) everything in the lake with Athena serving: too slow and pay-per-query; (c) lake for truth plus a versioned export loaded into Postgres: two systems, but each does what it's good at.
**Decision:** (c). Spark writes Iceberg; `export_serving` writes versioned Parquet; the loader builds `*_vN` tables and swaps views atomically.
**Consequences:** DRAFT (Claude; rewrite in your own words): Rebuilding Postgres from the lake is always possible, so the serving copy can be dropped, reloaded or re-versioned without data loss, and evals can pin a snapshot. The cost is two systems to operate, an export/load step that must stay idempotent, and a freshness lag equal to export plus swap time. Every serving table needs a version and a view swap, and nothing may write to Postgres as if it were authoritative.
**How to revisit:** if the serving subset outgrows one Postgres box, or the load and swap time exceeds the freshness target.

## ADR-002: Numbers come from a typed query plan compiled to SQL; the LLM never writes SQL on the main path (2026-11-16)
**Status:** accepted
**Context:** Free-form text-to-SQL is hard to verify and risky (wrong tags and periods, injection-shaped failures). The verifier needs to know exactly what a number means.
**Options considered:** (a) free-form text-to-SQL with guardrails; (b) an LLM-filled typed `QueryPlan` (enum-constrained metrics) + a deterministic compiler producing parameterized SQL and provenance expressions; (c) hard-coded intents only.
**Decision:** (b), with (a) as a guarded fallback behind a flag, measured separately.
**Consequences:** DRAFT (Claude; rewrite in your own words): The verifier can check each number against a plan and provenance expression, and the model's output space is constrained to enum metrics, which makes failures auditable and injection-shaped SQL off the main path. The cost is coverage: any metric, period rule or comparison the catalog and compiler don't express gets a refusal or falls to the guarded fallback, so the metric catalog and compiler become the bottleneck and need steady extension. The fallback must stay behind its flag and be reported separately in evals.
**How to revisit:** if plan coverage on real user questions stays below an acceptable level after extending the catalog.

## ADR-003: Apache Iceberg rather than plain Parquet for the lake (2026-11-16)
**Status:** accepted
**Context:** Restatements need upserts; evals must be reproducible against a past corpus; daily appends must be atomic.
**Options considered:** (a) plain Parquet + Glue partitions; (b) Iceberg; (c) Delta Lake.
**Decision:** Iceberg (Glue catalog support on AWS, EMR and Athena integration, MERGE, snapshots, time travel).
**Consequences:** DRAFT (Claude; rewrite in your own words): Restatements can be applied as MERGE upserts, daily appends are atomic, and evals can read a past snapshot via time travel. The cost is catalog and tooling friction (Glue catalog, EMR and Athena compatibility, local file-based catalog for dev) and table maintenance such as compaction and snapshot expiry. Spark, DuckDB and pyiceberg versions must stay compatible with each other.
**How to revisit:** if the tooling friction on EMR or Athena costs more than it saves.

## ADR-004: No Kafka in this project (2026-11-16)
**Status:** accepted
**Context:** Tracked companies file roughly tens to a few hundred 10-K/10-Qs per day in earnings season [estimate; replace with the M10 measurement]. Freshness target ≤ 24 h. One consumer.
**Options considered:** (a) Kafka/MSK streaming; (b) a daily scheduler + SQS fan-out with a DLQ.
**Decision:** (b). Streaming is shown in Project 2.
**Consequences:** DRAFT (Claude; rewrite in your own words): The design stays simple: one scheduler, SQS fan-out with a DLQ, and one consumer, which is cheap and easy to explain. **How to revisit:** sub-hour freshness requirements, many independent consumers, or a need for replayable event history.

## ADR-020: `fact_key` excludes the taxonomy year (2026-11-17)
**Status:** draft by Claude from the decisions on record (2026-11-17); Shekar to review and finalize the wording
**Context:** `fact_key` must group every reported version of one fact across filings, because `facts_history`, `n_versions`, `is_restated` and version selection all work per `fact_key`. A restatement changes the taxonomy year in `version` (`us-gaap/2022` in the original filing, `us-gaap/2023` in a later one). Measured on the 7 local quarters (`docs/milestones/M01-dq-report.md`, "Curated facts"): 8,229,693 `curated.facts` rows cover 8,053,335 distinct facts, 5,420,567 with one version, 1,795,462 with two, 181,400 restated. These counts are with the year stripped; they were not recomputed with the year in the key, so how many facts the year would have split is NOT MEASURED.
**Options considered:** (a) key over the full `version` string; (b) key over the year-stripped taxonomy family (`us-gaap`, `dei`, `custom`); (c) key over a normalized concept ID from a standard-taxonomy mapping.
**Decision:** (b). `fact_key = xxhash64(cik, tag, taxonomy, period_end, qtrs, uom)` with `taxonomy` the year-stripped family (`docs/plan/05_data_contracts.md` section 2.2). Including the year would put a fact and its own restatement under different keys, so `facts_history` would never group them and no restatement would be detected.
**Consequences:** A tag whose meaning changes between taxonomy years now shares a key across the years. Custom tags are keyed by `custom` plus the tag and CIK. The Spark and DuckDB twins must derive `taxonomy` identically; the differential test covers that. Option (c) is not built.
**How to revisit:** if a tag redefinition across taxonomy years shows up as a false restatement, move to (c) for the affected tags.

> Numbering note: ADR-005 is already reserved for "one EC2 box vs Lambda + Aurora" (`docs/plan/03_architecture_and_stack.md`, planned list above), so ADR-020 is numbered 020. Renumber if you prefer; the only other reference is the `taxonomy` bullet in `docs/plan/M01_xbrl_lakehouse.md` section 3.5.

## ADR-022: Deterministic ties and derived-Q4 eligibility and identity (2026-11-17)
**Status:** draft by Claude from the decisions on record (2026-11-17); Shekar to review and finalize the wording
**Context:** On 7 real quarters the Spark and DuckDB twins differed in 5,130 / 3,955 / 1,264 rows (`facts_history` / `facts` / `facts_dimensional`, both sides counted; `docs/milestones/M01-differential-analysis.json` at commit `f4daa7e`). By cause, summed over the tables: label-offset ties 9,792, fiscal-year ties 494 (+ 51 knock-ons), identity collisions 6. Two causes, both in the reference: (1) it broke ties (the label-offset mode, two FY rows of one filing after a fiscal-year change, 9M period-end groups) by list position, so its answer depended on input order; for three series it gave 2 different outputs over 60 random orders; (2) it derived Q4 from an FY row of any form, so a 10-Q's trailing-twelve-month value became a parent: 28,185 of 784,934 derived Q4 rows in the 7-quarter Spark `facts_history` came from forms other than 10-K, 10-K/A and 10-KT, and 175 `fact_id`s were shared by several rows, all involving a derived row.
**Options considered:** sort the reference's input vs give every `min`/`max` an explicit tie key vs leave ties undefined; restrict FY parents by form vs by whether the FY period end is a fiscal year end; put the 9M accession in the derived `fact_id` vs a flag column vs dropping derived rows from `facts_history`.
**Decision:** (1) Every input is sorted by (accession, value NULLs last, period end, quarters, cik, tag, taxonomy, uom) before any tie-sensitive step. The label-offset tie goes to the offset of the submission with the smallest accession; two FY rows go to the smaller value. These tie-breaks are stable, not business rules. (2) Derive Q4 only from an FY parent whose form is 10-K, 10-KT or 10-K/A, never from a 10-Q comparative. 20-F and 40-F are a deliberate scope exclusion, not an open question. (3) A derived Q4's `fact_id` is `xxhash64(fact_key, accession, nine_month_accession)`, so it cannot collide with a real fact. Rules 1 and 2 live in `pipelines/common/fiscal_ref.py` (applied by Shekar from `docs/proposals/ADR-022-fiscal_ref.diff`); rule 3 is in the twins and contract section 2.2.
**Consequences:** Derived Q4 rows in the 7-quarter Spark `facts_history` fell from 784,934 to 764,324, none from a non-annual form (was 28,185). 0 `fact_id`s are shared (was 175). Spark, DuckDB and the reference differ in 0 rows in all three tables on 2 and 7 quarters, with 0 unexplained differences; the reference run directly over 8,193 companies and 12,201,161 `facts_history` rows differs from DuckDB in 0 rows (2 quarters: 6,721 companies, 3,320,915 rows, 0). Q4 values that came from S-1s, 10-Qs, 20-Fs and 40-Fs no longer exist. Anything that stored a derived row's old `fact_id` must be rebuilt.
**How to revisit:** if Q4 from foreign annual reports or registration statements becomes a product requirement, widen the form set in `ANNUAL_FORMS`; if the tie rules matter to a real answer, replace them with a business rule.

## ADR-017: As-originally-reported vs restated values (2026-11-17)
**Status:** draft by Claude from the decisions on record (2026-11-17); Shekar to review and finalize the wording
**Context:** A company restates a figure in a later filing (a new 10-K, a 10-K/A, or the comparative column of the next year's report). Both values are in the data and finance users care which one an answer uses. Measured on the 7 local quarters (`docs/milestones/M01-dq-report.md`, "Curated facts"): 181,400 of 8,053,335 distinct facts are restated.
**Options considered:** (a) always the latest value; (b) always the original; (c) default to the as-originally-reported value, cite its native filing, and surface the restated value when the fact is restated.
**Decision:** (c). Answers default to the as-originally-reported value and cite the native filing, because that matches the cited document; when `is_restated` is true the restated value is surfaced next to it. `curated.facts` keeps both the latest and the original version per `fact_key` (one row when they have the same value, two otherwise); `facts_history` keeps every version (`docs/plan/05_data_contracts.md` section 2.2).
**Consequences:** The M4 gold set takes the original value for restated facts (`docs/plan/M04_eval_harness.md`). Answers about a restated fact carry two values and two citations.
**How to revisit:** if users ask for current values by default, flip the default and keep the same two columns.

## ADR-023: Filing fiscal labels reuse the fiscal_ref rules, so text and facts agree (2026-11-17)
**Status:** proposed
**Context:** `curated.filings` and `curated.chunks` need `fiscal_year` and `fiscal_period` (`docs/plan/05_data_contracts.md` section 2.2), and the engine joins text to numbers by those labels. `curated.facts` already labels facts with `fiscal_ref` (`y_end` plus a per-company label offset, M01 section 3.5 rules 1-4). A unit test asserts a filing's labels equal `derive_fiscal`'s labels for the same filing's facts.

## ADR-026: Title-only and cross-reference heading formats are scoped out of M2 (2026-11-17)
**Status:** proposed
**Context:** The section chain needs an `Item N` heading in the body. In the 150-filing sample (`docs/milestones/M02-blast-radius.json`) 13 filings still miss a required item after the two cheap fixes (14 before: `M02-blast-radius-before-fix.json`): financials 6 of 43 (7 before the Allstate fix), utilities 2 of 26, other 5 of 79; the 18 multi-registrant covers never fail. Causes (`summary.by_cause`): 11 only a TOC or index row, 5 mentioned only, 13 never written. Text before the first detected heading is not chunked: for the 11 filings missing Item 1 or 1A it is 8.1% to 29.8% of the document in nine, 100% for Citigroup, 1.0% for Synchrony (a complete filing: median 2.5%).
**Options considered:** (a) a title-based detector in M2: recovers some, risks false positives on the 138 working filings, unmeasurable without labels. (b) Scope out: these filings already parse `partial` or `no_sections`. (c) Chunk pre-heading text unlabeled: cheap, loses the section label.
**Decision:** (b). Title-only and cross-reference formats stay unsupported. Those filings' Item 1 and 1A text is NOT retrievable: it precedes the first detected heading and is not indexed (Citigroup: all of it). A missed later item is indexed under the previous section's label.
**Consequences:** (draft by Claude for Shekar to review and rewrite) In the 150-filing sample 13 filings (8.7%) still lack a required item, mostly financials (6 of 43) and utilities (2 of 26). For those filings the text before the first detected heading is not indexed (8.1% to 29.8% of the document in nine of them, 100% for Citigroup), and a missed later item is indexed under the previous item's label, so a section filter can return text with the wrong label or nothing. Nothing in the engine knows a filing is incomplete beyond its `partial` / `no_sections` parse status, so a question about one of these filings can be refused or answered from the wrong section, and that would look like a retrieval miss in the M4 eval. Stays unhandled: every filing whose items appear only in a table of contents, in prose, or under titles with no `Item N` text. What it buys: no title-based detector to maintain and no false-positive risk on the filings that parse `ok`. The prevalence in the full 500-company corpus is NOT MEASURED.
**How to revisit:** a later heading-detector improvement, not an M2 blocker; sooner if the M4 question-level eval misses on these filings.

## ADR-027: Spark jobs run on AWS Glue 5.0 because an Organization policy denies EMR Serverless (2026-11-20)
**Status:** proposed
**Context:** The account (`019593222039`) is a member of an AWS Organization, on the Free plan. A service control policy explicitly denies `emr-serverless:*` (`aws emr-serverless list-applications` returns an explicit deny in SCP `p-42ggg3sk`, 2026-11-20), so the application in M01 section 3.8 and ADR-024 cannot be created. Glue is on the Free-plan list (`04_aws_and_cost_plan.md` section 1) and its jobs are billed per DPU-second with a 1-minute minimum.
**Options considered:** (a) ask for the SCP to be lifted: outside my control and slow. (b) run Spark on the EC2 serving box: a second always-on cost and the box does not exist before M9. (c) Glue Spark jobs running the same modules: no new service, same Iceberg-on-Glue-catalog tables. A smoke run showed the Glue 5.0 runtime accepts `pipelines/` unchanged (including the `applyInPandas` path in `fiscal.py`) with no extra Python modules.
**Decision:** (c). `pipelines/common/spark_session.py` gains `env="glue"` (the `emr` Glue-catalog settings; the Iceberg jar comes from `--datalake-formats iceberg`). `pipelines/glue/*_job.py` are thin entry points over the unchanged `pipelines.spark` jobs; `scripts/glue_deploy.sh` publishes them and `pipelines.zip` to `s3://<lake>/scripts` and `artifacts/glue`. `infra/terraform/modules/glue` defines `edgarqa-fsds-to-iceberg` and `edgarqa-normalize-facts` (G.1X, 4 workers, 30 minute timeout, no retries). The EMR entry points, module and image stay in the repo, disabled (`create_emr_application = false`). `fsds_to_iceberg` now reads `s3://` sources, and both jobs take a subset (`--ciks`, `--fiscal-years`, `--limit-filings`) that smoke runs write to `raw_smoke` / `curated_smoke`, never to `raw` / `curated`.
**Consequences:** (draft by Claude for Shekar to review and rewrite) Glue is the only Spark runtime until the Organization policy changes: the EMR entry points, module and image stay in the repo disabled, which is code to keep consistent but never run. Code under `pipelines/spark` must run on the Glue 5.0 runtime (Python 3.11) as well as locally (Python 3.12), and the parser jobs install their PyPI dependencies at job start with `--additional-python-modules`. Deploying is a manual step (`make glue-deploy`, a dry run unless `YES=1`), so the code on S3 can lag the repository (it did after the Berkshire parser fix). Any other filer with the same cross-reference format is NOT MEASURED, so the corpus-wide share is unknown until the full parse. ## ADR-031: A contents table no longer moves the 10-Q part, and a missing Item 1 heading is implied (2026-11-21)
**Status:** proposed
**Context:** The full-corpus parse (13,239 filings, `docs/milestones/M02-fullcorpus-metrics.json`) left 11,178 filings `ok`, 84.4% strict against a 95% target, and 1,226 10-Qs in 78 of 500 companies missing both `P1-1` and `P1-2`. ADR-028 had attributed that symptom to JPMorgan's cross-reference format. Reading the parser on two affected filings (Humana `0000049071-26-000066`, Moderna `0001682852-26-000197`) showed two other defects. **Options considered:** (a) scope the part to a contents table, read an item as Part I until a Part line says otherwise, and imply `P1-1` after the contents table (chosen). (b) The title-based detector of ADR-028(b): the larger piece of work, and it needs gold labels. (c) Keep the old chain whenever the new one covers less text: leaves the bug in place as a fallback. (d) Fix (1) only: tested first and rejected, because 40 of the affected filings (11 CIKs) then lost about 48% of their text from the index (their old result put everything under a contents-table `P2-6`, wrong but retrievable; the new one found `P1-2` and later but left the financial statements before the first heading).
**Decision:** (a), in `pipelines/parsing/sections.py`: a table block that names two or more different Parts keeps its part to itself (`_is_contents_table`); before any Part line a 10-Q item is Part I; and `_imply_part1` starts `P1-1` at the block after the contents table (the first run of candidates at most `TOC_GAP_BLOCKS` = 20 blocks apart) when the first chosen section is `P1-2` or later and at least `MIN_IMPLIED_CHARS` = 5,000 characters lie between. The implied section has an empty `heading_text`, no anchor, and the canonical title. Both constants are judgement, not fitted: in the 486 filings where `P1-1` was implied the smallest was 5,693 characters, so the 5,000 guard never fired on the evidence; it is covered by a unit test (`tests/unit/parsing/test_part_state.py`, mutation-checked). 10-Ks are untouched. **This is the last parser fix for M2.**
**Verification (before any cloud run):** `eval/parser_diff.py` ran the committed and the patched detector over 2,661 stored filings (`docs/milestones/M02-part-state-diff.json`): the 1,226 affected 10-Qs, 1,000 seeded previously-`ok` 10-Qs, 150 `partial` 10-Qs missing one item, 150 blast-radius 10-Ks and the 135 local filings. Previously-`ok` filings changed: **0**. **Gate relaxation, recorded as such:** the gate as first worded was "no filing loses block coverage". It failed literally: 417 changed filings lost block coverage (66,245 characters in total, at most 0.53% of a filing). The heading regex still lives in three places (ADR-029); the part logic lives only in `sections.py`.

## ADR-032: Chunk embeddings run on Glue with the quantized bge ONNX staged in S3, not baked into an image (2026-11-21)
**Status:** proposed
**Context:** M03 §3.1 assumes a custom EMR image with fastembed and the model weights baked in. EMR Serverless is denied by an Organization policy (ADR-027), and Glue 5.0 has no custom images. Reading the installed `fastembed==0.9.1` shows two further facts: the name `BAAI/bge-small-en-v1.5` resolves to the **quantized** build `Qdrant/bge-small-en-v1.5-onnx-Q` (`model_optimized.onnx`), not the fp32 model; and `query_embed` adds no BGE query instruction for this model, so `query_embed` and `passage_embed` give the same vectors (ADR-033). `curated.chunks` holds 2,856,686 chunks, none above 400 tokens (counted with the bundled bge tokenizer, so no truncation against the 512 limit).
**Options considered:** (a) let each Glue worker download the model from Hugging Face at start: no staging, but a Hugging Face dependency on every worker and no sha pin on what produced the vectors (the PyPI install in (b) is also a network dependency, accepted below). (b) Stage the model files once in `s3://<lake>/artifacts/models/bge-small-en-v1.5/`, pinned by sha256 like the tokenizer, and have each Python worker copy them to local disk once (chosen). (c) Embed on the laptop only (runbook option B): same vectors, but it drops the distributed-embedding story and T2b.
**Decision:** (b). `pipelines/spark/embed_chunks.py` runs as a Glue 5.0 job (`mapInPandas`, one model load per Python worker, ONNX threads = 1, batch 256 at first and length-sorted batches of 32 from 2026-11-22 (ADR-037), `passage_embed`, L2 normalization), incremental through a `LEFT ANTI JOIN` on `chunk_id`. `fastembed` and `onnxruntime` come from the job's `--additional-python-modules` at the versions in `uv.lock`. The export manifest records `embedding_artifact` (HF repo, file, sha256). Every chunk is embedded, including degenerate ones, so "missing = 0" stays checkable (ADR-035 drops them at export).
**Consequences:** (draft by Claude for Shekar to review and rewrite) The vectors come from a quantized model: quality against the fp32 model is not measured in M3 and is decided in M4 against the FinanceBench gold (HNSW recall in M3 measures the index, not the model). Staging adds a one-time S3 upload and a sha check. `pip install` of fastembed on Glue's Python 3.11 is untested until the smoke run, and it is a PyPI download at every job start: the top-level packages are pinned to `uv.lock` but their transitive dependencies are not, a risk I accept for M3 because the vectors' identity is protected separately (the staged ONNX file is sha-pinned, and the x86-vs-ARM agreement check and the smoke cross-check would show drift). Embeddings are matched to chunks by `chunk_id` alone, and `chunk_embeddings` has no text hash (contract §2.2): if a re-parse changes a chunk's text but keeps its id (as ADR-031 did for some filings), the old vector stays and "missing = 0" still holds. So after any re-parse, delete the embeddings of the re-parsed filings (or recreate the table) before the next run; the export inner-joins to `chunks`, which drops vectors of ids that no longer exist. The job must also run alone per output table: its insert-only MERGE does not stop two overlapping runs from inserting the same chunks twice, so the Glue job sets `max_concurrent_runs = 1`, and a laptop run must not overlap a Glue run on the same table. **Measured result of the served run (2026-11-22, `M03-embed-metrics.json` `served_run`):** 1,097,376 chunks embedded in 4 waves on 20 G.1X workers (all 20 allocated), 39.99 DPU-hours = $17.59 at $0.44, **$1.60 per 100k chunks and 9,150 chunks/min over whole runs** (2.00 h of run time), about 12% above the pre-run estimate. The speedup from length-sorting is 1.19x (same batch size, same load); batch 32 was needed to use all four cores of every executor without running out of memory, not just to go faster. The 1.56x from the local laptop is not a Glue result and is not part of this number. Cost is measured per run from `dpu_seconds` and `infra/pricing/glue.yaml`; a small smoke run's $/100k chunks includes startup, the pip install, the table scan and the model load, so it is an upper bound and T2b is taken from the full run. The embed-all cost gate (all 2.86M chunks against the served 1.1M) is decided after the smoke and recorded in the devlog.
**How to revisit:** if M4 shows the quantized vectors lose retrieval quality against fp32, re-embed the served chunks with fp32 weights (a second Glue run priced from the first); if Glue gains a custom-image option or EMR becomes available, move the weights back into an image.

## ADR-036: Embeddings agree across x86 (Glue) and ARM (laptop) to cosine 0.9999994, so one set of vectors serves both (2026-11-22)
**Status:** proposed
**Context:** The vectors come from a quantized ONNX model (ADR-032). Quantized int8 kernels can differ between x86 and ARM, and the future API box that embeds queries may be ARM (the M9 plan names a Graviton `t4g`), so a query embedded on one architecture must still match passages embedded on the other.
**Options considered:** (a) assume agreement. (b) Measure it on the smoke run before the full run and stop if any chunk falls below a cosine gate (chosen). (c) Embed everything on one architecture only.
**Decision:** (b). `scripts/check_cross_arch.py` read 200 chunks of the Glue smoke run (`jr_04e0eccf...`, driver log `driver platform x86_64, onnxruntime 1.32.0, fastembed 0.9.1`), spread over four token bins, re-embedded them on the Mac (arm64, same onnxruntime and fastembed versions, same ONNX sha256) and compared row by row. Gate: every chunk at cosine >= 0.9999 (`pipelines/common/vector_agreement.py`).
**Result** (`docs/milestones/M03-embed-metrics.json`, `cross_arch_agreement`): n = 200, **min cosine 0.9999994, mean 0.9999997**, p1 0.9999995, **0 chunks below the gate**, largest single-component difference 6.4e-4; the control (the same Mac with 1 thread against 4 threads) has min cosine 1.0, so the differences are architecture, not threading.
**Consequences:** (draft by Claude for Shekar to review and rewrite) The full run is not blocked and an ARM query embedder can use the same index. The vectors are not bit-identical across architectures (differences of order 1e-4 per component), so a test must compare vectors by cosine, never by equality. The check covers 200 chunks of one smoke run and one pair of architectures; the final query-time architecture is decided in M9 and should re-run the script against the actual box.
**How to revisit:** re-run `scripts/check_cross_arch.py` on the real serving box in M9, and whenever the onnxruntime or fastembed pin changes.

## ADR-038: The loader refuses to reload only the live version; the previous version may be reloaded (2026-11-22)
**Status:** proposed
**Context:** The contract's `corpus_state` rules (retention = keep `live` and `previous`, never "N-2") said that loading N when N is one of (live, previous) is refused. M3 requires the sequence load v1, swap, load v2, swap, roll back to v1, then rerun v2 and show it adds nothing. After the rollback v2 is the `previous` version, so the old rule would refuse that rerun instead of showing that a reload replaces rather than appends.
**Options considered:** (a) keep the refusal for both live and previous: safest for the rollback target, but a corrupt or partial `previous` could never be repaired without first swapping; (b) refuse only the live version (chosen); (c) refuse nothing: dropping live tables under the views would break serving.
**Decision:** (b). `load_version` drops and recreates `facts_vN`, `chunks_vN` and `companies_vN` for any N that is not live, and raises `LoadError` for the live version. A failed load drops its own tables, so a failed reload of the previous version leaves no rollback target until it is repeated; `swap` and `rollback` require all three tables of the target to exist. Retention is unchanged: after a swap or rollback every version not in (live, previous) is dropped.
**Consequences:** (draft by Claude for Shekar to review and rewrite) A reload of the previous version removes the rollback target for the duration of the reload (about the load time) and for good if the reload fails; the operator must not reload `previous` while depending on a rollback. The integration test pins the sequence above.
**How to revisit:** if rollback must always be available, load into a differently named staging version and rename, at the price of twice the disk during a load.

## ADR-039: Bulk load with psycopg COPY from Parquet via CSV, not DuckDB (2026-11-22)
**Status:** proposed
**Context:** M03 §3.3 asks to pick psycopg COPY or DuckDB's Postgres extension for the load and record it. The export is Parquet on S3; the target has a `halfvec(384)` column, `text[]` and `bigint[]` columns, and chunk text with newlines, tabs, quotes and backslashes.
**Options considered:** (a) per-row `copy.write_row`: simple, but tens of millions of Python cell conversions. (b) DuckDB reading Parquet and writing through its Postgres scanner: no Python in the loop, but another binary on the box, no `halfvec` support that I verified, and a second place where escaping can go wrong. (c) pyarrow reads record batches; scalar columns are written as quoted CSV by pyarrow's C++ writer; the three nested columns are turned into Postgres literals first (`halfvec` as `[x1,...,x384]` after a float16 cast, which is the precision halfvec stores anyway); the CSV is streamed into `COPY ... FROM STDIN (FORMAT csv, NULL '')` (chosen).
**Decision:** (c) in `serving/load/load_snapshot.py`. Every non-null value is quoted so an empty string differs from NULL. The integration tests round-trip text with tabs, newlines, backslashes and quotes byte for byte.
**Consequences:** (draft by Claude for Shekar to review and rewrite) One Python dependency stack (psycopg, pyarrow) that the tests already use. The vector text conversion is still a Python loop over rows; its cost is measured in the load report (`copy_chunks`), not assumed. float16 rounding happens in numpy before Postgres parses the text; the result equals Postgres' own float4-to-half rounding because both round to nearest even (not separately verified beyond the recall measurement).
**How to revisit:** if `copy_chunks` dominates the load time, write halfvec in COPY binary format with the pgvector Python adapter.

## ADR-040: HNSW index m=32, ef_construction=128 and default ef_search 800; recall@10 reaches 0.95 only at the top of the ef_search range (2026-11-23)
**Status:** proposed
**Context:** The runbook's index (`m=16, ef_construction=64`) was built on the 1,081,461-chunk corpus (378 s, 1,110 MB) and measured against exact search over the same stored `halfvec(384)` column (index scans off, a sequential scan), on 200 + 200 deterministic chunk-derived queries (spans of chunks, and the harder case of two unrelated spans joined), with 10,000-resample bootstrap CIs (`docs/milestones/M03-serving-bench.json`). The DoD asks for recall@10 >= 0.95 at the chosen `ef_search`, or a documented result. The first bench also revealed two flaws of mine, both fixed: the query sample was not deterministic (a parallel scan without `ORDER BY`), so one early run read 0.955 at ef 800 where the deterministic runs read 0.9245; and the earlier curve was cold at the first `ef_search`.
**Options considered:** (a) keep m=16/64 and report it: recall 0.9245 [0.899, 0.948] at ef_search 800 and 0.9315 [0.906, 0.954] at 1000 (pgvector's maximum), below the gate on the conservative set. (b) Rebuild with m=32, ef_construction=128 (chosen): 1,129 s to build, 1,295 MB. (c) Keep raising m and ef_construction: not done, per Shekar's rule not to keep raising them on the 2-vCPU box. (d) Switch to float32 `vector(384)`: tested as a diagnostic only (see Result), not built. fp32 re-embedding was explicitly out of scope for M3.
**Decision:** (b). Defaults in the contract and the loader are now m=32, ef_construction=128, and the default `ef_search` is **800**: the smallest tested value whose recall on the conservative query set reaches 0.95 (0.9615, CI [0.942, 0.978]; dense search p50 21.8 ms, p95 30.7 ms on a flex instance, preliminary). The gate is met by the point estimate only: at ef_search <= 200 the recall is 0.8915 [0.859, 0.921], well under 0.95, and at 800 the interval's lower bound is 0.942. The documented outcome per the DoD is therefore "reaches 0.95 at ef_search 800, not below ~400".
**Result of the apples-to-apples question:** recall was already measured against exact search on the same halfvec column, so it contains no fp16 penalty. A direct diagnostic on the same queries (`serving/bench/halfvec_check.py`) found halfvec exact vs float32 exact top-10 overlap 0.990 (self-span) and 0.9955 (mixed-pair), and HNSW recall against float32 truth within 0.001 of its recall against halfvec truth. Halfvec storage costs about 0.5-1% of top-10 overlap; the shortfall is the HNSW approximation, not the storage type. Tie-aware recall (counting an equally near duplicate as a hit) is only about 0.01 higher than set recall, so near-duplicate 10-K chunks do not explain it either.
**Consequences:** (draft by Claude for Shekar to review and rewrite) Queries pay about 22-31 ms for the dense leg instead of 5-10 ms; the build is about 3x slower and the index 17% larger. A load on the box now takes about 10 minutes longer. Retrieval quality against the FinanceBench gold, not set overlap with an exact scan, is what M4 should use to decide whether the recall loss matters and whether `vector(384)` or a higher `ef_search` is worth it. The latency and build numbers come from a Free-plan `m7i-flex.large` and are preliminary.
**How to revisit:** in M4, measure answer-level retrieval against FinanceBench gold at ef_search 100, 200 and 800; if 200 loses nothing, lower the default. A larger box or `max_parallel_maintenance_workers` above 2 would speed a rebuild but not change recall.

## ADR-041: One refusal shape everywhere: reason, found, missing (2026-11-23)
**Status:** accepted
**Context:** Contract 4.3 showed only `"refusal": null`; M05 says the composer refuses "with what was found" and M06 says the verifier's sufficiency check refuses with `found` and `missing`. The M4 harness and baseline needed a concrete type before the engine exists, and the API response (section 5) returns the same field.
**Options considered:** (a) a bare string reason: simplest, but the verifier's partial-answer refusal ("found X, missing Y") can't be scored or rendered. (b) `found` as a list of Claim objects: duplicates provenance already in `claims` and lets a refusal carry unverified provenance. (c) `{reason, found: [str], missing: [str]}` with `found` holding the text of surviving claims (chosen).
**Decision:** (c), in `app/engine/answer.py` (`Refusal`) and `05_data_contracts.md` 4.3 and 5. The composer (M5), the verifier's sufficiency refusal (M6) and the API use the same shape; M06 §3 now points to it. Eval treats `refusal != null` as a refusal regardless of content. A refused answer may still carry claims (a partial answer), so "refused" and "has claims" are independent; metrics must not infer one from the other. The correctness judge decides a refusal in code without a model call, so no `found` or `missing` text reaches any judge prompt.
**How to revisit:** if the UI needs to link each `found` entry to its claim, add an optional `claim_ids` list to `Refusal` (a contract change: 05 first).


## ADR-042: Metric catalog after the M4 accounting review: six concept calls (2026-11-23)
**Status:** proposed (Shekar applies the catalog diff; `metric_catalog.yaml` is his file)
**Context:** The tag-chain review packet (`docs/m4/catalog_review_packet.md`) went to an accounting reviewer. Her memo, distilled in `docs/m4/m4_catalog_decisions.md`, makes one point: verifying that a number *exists* in EDGAR is not verifying that it *means* what the question asks. Her term for a source-only match is "source-matched"; "verified" is reserved for a match on scope, period, unit, entity and interpretation as well. The initial catalog treated `tags` as a first-populated-wins chain and mixed concepts inside chains.
**Options considered:** (a) keep the chains and rely on the companyfacts second-source check. Rejected: the same tag sits on both sides, so a wrong concept passes. (b) narrow every chain to one tag. Rejected: it loses real coverage where two tags are the same concept. (c) make the six calls below, give distinct presentation bases their own metrics, and resolve multi-tag chains instead of taking the first tag (ADR-043). Chosen.
**Decision:** The six calls:
1a. **Tax-inclusive revenue** (`RevenueFromContractWithCustomerIncludingAssessedTax`) leaves `revenue` and becomes `revenue_including_assessed_tax` (`presentation_basis: including_assessed_tax`). The memo's Philip Morris example: $29.6B excluding vs $79.8B including taxes (2.69x).
1b. **Bank revenue** (`RevenuesNetOfInterestExpense`) leaves `revenue` and becomes `bank_revenue_net_of_interest_expense` (`presentation_basis: net_of_interest_expense`). It is a real revenue measure for banks, not comparable to industrial sales.
2. **Cost of revenue** prefers `CostOfRevenue`, the consolidated total, only conditionally. A material, unreconciled disagreement with `CostOfGoodsAndServicesSold` abstains. The memo's Block example: $6.76B vs $143.9M.
3. **Gross profit = revenue - cost of revenue** stays as `fallback_formula`, under `only_if: [same_entity, same_period, same_currency, same_scope, inputs_verified]`, and its result is labelled `fallback_result: derived`.
4. **Total liabilities** (`Liabilities`) is kept as the consolidated balance-sheet total, an instant (qtrs = 0).
5. **Shares outstanding** (`CommonStockSharesOutstanding`) is kept as the balance-sheet-date count. It is distinct from the dei cover-page count and from the weighted-average count.
6. **Long-term debt** (`LongTermDebtNoncurrent`) is kept, under its precise label "Noncurrent long-term debt": it excludes the current portion and leases.

The inert deprecated tags `SalesRevenueNet` and `CostOfGoodsSold` (0 facts in the packet) are dropped.

The catalog model (`eval/gen/catalog_review.py` `MetricDef`, 05 §4.2) gains the optional fields `presentation_basis`, `only_if` and `fallback_result`. They enter `definition_sha` only when set, so no existing verification is invalidated by the model change; the changed metrics get new shas and need re-review. The proposed catalog edit is `docs/m4/metric_catalog_proposed.patch` (`git apply`); a unit test applies it to a copy and loads the result.
**Consequences:** (draft by Claude for Shekar to review and rewrite) Revenue questions for banks and tax-inclusive filers now ask for a named concept, not "revenue". That is less coverage for generic `revenue` and fewer silent concept swaps. `numeric_metrics_verified.txt` must list the new shas; the memo says to hold `revenue` and its dependents (gross profit, margins) until the resolver has been audited on conflicting filings (`make_numeric_set --resolver-audit K`). Contract 05 §4.2 was updated before the model, per the contracts-first rule.
**How to revisit:** if the resolver audit shows `RevenueFromContractWithCustomerExcludingAssessedTax` and `Revenues` disagree for structural reasons in one sector (for example insurers), split that sector's revenue into its own metric, as was done for banks.

## ADR-043: Multi-tag metrics are resolved by statement presentation and the gross-profit identity, or abstain (2026-11-23)
**Status:** proposed (drafted by Claude, pending Shekar). Binds M4 gold generation; M5 decides the engine's own resolution, and M05 §3.4's "first tag with a value wins" (`ORDER BY array_position ... LIMIT 1`) is superseded for Shekar to edit
**Context:** The review found that even the top two revenue tags are not synonyms: `...ExcludingAssessedTax` and `Revenues` differ by more than 1% in 849 of 1,328 same-period pairs (63.9%, per the memo in `docs/m4/m4_catalog_decisions.md`). An unconditional priority chain therefore puts a component or a different scope into gold whenever the first tag happens to be populated.
**Options considered:** (a) first populated tag wins (the old contract text). Rejected for the reason above. (b) always the largest value. Rejected: it picks tax-inclusive or gross-of-something figures. (c) the review's selection sequence: candidates for the exact entity and period, the statement presentation, a calculation check, then abstain (chosen).
**Decision:** `eval/gen/revenue_resolver.py` implements the sequence. It applies to every metric with two or more tags (after ADR-042, `revenue` and `cost_of_revenue`), for one (cik, fiscal_year, fiscal_period):
1. Candidates come from the metric's chain only.
2. Candidates are screened and versioned by ADR-044.
3. Candidates that agree within the metric tolerance are one number; the chain order only picks which tag to cite.
4. On a material disagreement, the tag the filing presents on its income statement wins. The test is presence on the statement, not that the line is the total; see the limits below. The source is FSDS `pre` with `stmt = 'IS'`, not parenthetical, read from the local `raw.fsds_pre` snapshot. If the gross-profit identity (revenue - cost of revenue = `GrossProfit`) contradicts the presented tag while another candidate satisfies it, the resolver abstains.
5. Otherwise the candidate that satisfies the gross-profit identity wins.
6. Otherwise, for `revenue` only, `Revenues` is the total: it is the income-statement top line and contract revenue (`RevenueFromContractWithCustomerExcludingAssessedTax`) is a component of it (`total_tag_is_top_line`; amended 2026-11-23, Shekar chose option a). Two guards apply:
   - If `Revenues` is below contract revenue for the same (cik, period), the resolver abstains (`total_below_component`). This guard is unconditional for the pair: it is checked right after the agreement step, before presentation and the identity, so neither can pick from an inconsistent pair.
   - If the gross-profit identity can be checked and `Revenues` fails it, the resolver abstains (`total_fails_gross_profit_identity`). The identity stays a confirming check: when it picks contract revenue at step 5, step 6 never runs.
   The rule is scoped by `TOTAL_OVER_COMPONENT` in `eval/gen/revenue_resolver.py`, so `cost_of_revenue` has no such rule.
7. Otherwise it abstains (`conflicting_candidates`), with the candidates exposed in `numeric_auto.abstentions.jsonl`.

`make_numeric_set --resolver-audit K` writes `eval/sets/drafts/revenue_resolver_audit.md`, a sample of decisions on conflicting filings, for the memo's final step: audit the resolver before any revenue gold is generated.
**Consequences:** (draft by Claude for Shekar to review and rewrite)
- The numeric set loses the hardest revenue rows instead of carrying wrong gold. Abstentions are counted and shown, not hidden.
- Presentation data covers only filings in the local `fsds_pre` snapshot: 48,722 distinct `adsh`, counted 2026-11-23 with DuckDB over the current snapshot of `warehouse/raw/fsds_pre`. Outside it, only agreement and the identity can resolve a conflict, so coverage is reported (`presentation_known` / `presentation_unknown` in the summary).
- The FSDS calculation linkbase is not loaded. The gross-profit identity is the only calculation check, so a conflict with no `GrossProfit` fact and no presentation data abstains.
- A property test asserts that the outcome never depends on input order, the signature of first-populated-wins.
- **Option (a), amended 2026-11-23.** The resolver audit (`eval/sets/drafts/revenue_resolver_audit.md`) found 482 materially conflicting cases. The identity resolved 48, presentation resolved none, and 434 abstained. A read-only diagnostic in the same session, not recorded in the audit file, found that in every conflict with presentation data both revenue tags are on the income statement. The samples include REITs whose contract revenue is a small slice of `Revenues` (UDR FY2024: $8.3M vs $1.67B). So step 6 adds `Revenues`-as-top-line, with the guards above. Presentation (step 4) still runs before step 6, but the below-component guard runs before both. The number of cases step 6 now resolves is NOT MEASURED; it needs a re-run of the audit.
- Known limit, "presented" is not "total": if a statement shows only a component line (say `CostOfGoodsAndServicesSold`) and the total `CostOfRevenue` sits in the notes, with no `GrossProfit` fact to contradict it, the presented component wins. In a conflict, chain order does not override presentation. So ADR-042's "prefer `CostOfRevenue`" holds only for ties and for cases the identity settles. The resolver audit is where this shows up.
- Deferred to M5/M6 and recorded here rather than built now: the typed metric registry, a dimensional consolidation policy (today `facts` is consolidated by construction), and the four verification states (source-matched / concept / period-scope / verified).
**How to revisit:** if abstentions starve a stratum, load the calculation linkbase (FSDS has no `cal` table; it would come from the XBRL instance) before loosening the abstain rule.

**Decision 2026-11-23 (Path B, Shekar):** M4 numeric gold is the 17 verified metrics only (`eval/gen/numeric_metrics_verified.txt`). `revenue`, `cost_of_revenue`, `gross_profit` and every ratio that divides by revenue (`gross_margin`, `operating_margin`, `net_margin`, and any compare question that needs revenue) are excluded from M4 gold.
- **Why:** the resolver audit found 482 materially conflicting (cik, period) cases across `revenue` and `cost_of_revenue`, of which the gross-profit identity resolved 48, presentation resolved 0, and 434 abstained (`eval/sets/drafts/revenue_resolver_audit.md`). Option (a) (`total_tag_is_top_line`) was added after that audit and has **not been re-audited**: how many of the 434 it resolves, and how many it resolves wrongly, is NOT MEASURED. Revenue gold would rest on an unmeasured rule.
- **What does not change:** `numeric_metrics_verified.txt` (no revenue-family line), `revenue_resolver.py` and its tests stay as committed. The resolver remains available to the M5 engine design. No `--resolver-audit` run is part of M4.
- **Consequence:** the `ratio` template bucket (60 of the 300 target rows, `TEMPLATE_SHARES` in `eval/gen/make_numeric_set.py`) is empty: ratio items come only from verified metrics that have a `formula`, and the three margins are the only formula metrics in the catalog. The set therefore has fewer than 300 rows. The single_value, growth and compare buckets are unaffected because the 17 verified metrics remain. The produced row count and the shortfall are reported with the set, not backfilled with other metrics.
- **How to revisit:** after the project ships. Re-run `--resolver-audit` with option (a) in place, and read the sample by hand before adding any revenue-family metric to the allowlist.

## ADR-044: Data-quality policies for numeric gold: scope, periods, versions, tolerances (2026-11-23)
**Status:** proposed (drafted by Claude, pending Shekar). Supersedes M04 §3.3 "Keep `tolerance_rel = 0.01`" and §3.7's "within `tolerance_rel`" for Shekar to edit
**Context:** The review listed safeguards that a source match does not provide. The cases: 22 FY rows with `qtrs = 0` on duration metrics (revenue 1, net_income 1, income_tax 2, capex 1, dividends 17); EPS facts that may carry `USD` instead of `USD/shares`; restatements; segment values; margins from -1,399% to 9,587%; and a flat 1% tolerance that hides material errors on large values and misjudges rounded per-share figures.
**Options considered:** fix the rows in the lake (rejected: M4 must not rebuild M1 at this stage), or screen at generation time and log every rejection (chosen). For tolerance: a flat 1% (rejected), exact match (rejected: answers round), or metric-aware tolerances (chosen).
**Decision:** `eval/gen/numeric_policy.py`, applied by `make_numeric_set.py`:
- **Scope.** Only the `facts` view (consolidated: `coreg IS NULL`, no segments, 05 §2.2), never `facts_dimensional`, and only the `us-gaap` taxonomy.
- **Period.** FY requires qtrs = 4 and Q1-Q4 require qtrs = 1. H1/9M and year-to-date amounts are never used as a quarter. A derived Q4 (`derived_from` set) is excluded unless `--allow-derived-q4` is passed.
- **Quarantine.** qtrs = 0 on a duration metric, a unit mismatch, and qtrs != 0 on an instant are quarantined row by row to `numeric_auto.quarantine.jsonl`. Every other exclusion is counted by reason.
- **Versions.** The declared policy is `as_filed` (ADR-017): gold is the originally filed value, `latest_value` records the restatement, and a restated row's question says "as originally reported". `--policy latest_restated` is the alternative, one policy per set. The target is 20 restated rows at n = 300 (`RESTATED_TARGET`); fewer are drawn when restated facts are scarce.
- **Tolerance.** A value is correct when it is within `max(tolerance_abs, tolerance_rel * |gold|)`:
  - USD and share amounts: `rel` = 0.0005 (4 significant figures) and `abs` = 0.5, half a base unit, so a gold of 0 needs an exact 0. A first draft also inferred the filer's reporting scale from trailing zeros. The review showed this overstates the scale for round values: a gold of 0 or 3,000,000 got a tolerance of ±500,000. It was dropped.
  - Per-share amounts: `abs` = $0.005.
  - Ratios and growth: `abs` = 0.0005 (0.05 percentage points).
  - Two candidate tags disagree materially when neither tolerance accepts the other.
- **Denominators.** Ratios and growth abstain when the denominator is <= 0 or below $1M (`near_zero_denominator`). Each abstention is recorded with its reason (growth abstentions carry a `growth:` prefix). Margins are never clamped.
- **EPS units (amended 2026-11-23, Shekar approved option a).** FSDS records per-share amounts with uom `USD`. In `raw.fsds_num`, `EarningsPerShareBasic` has 176,845 `USD` rows and `EarningsPerShareDiluted` 165,261, plus 1,652 across both tags in other currencies, and neither has a `USD/shares` row. SEC companyfacts files the same facts under `USD/shares`: one fetch through `sec_client` of CIK 320193 (Apple) showed `units: ['USD/shares']` for both tags. The query, snapshot id, per-currency counts and the companyfacts units are in `docs/m4/eps_units_check.json` (2026-11-23). The exact-unit rule would therefore have quarantined every EPS fact.
  - For metrics whose unit is `USD/shares` only, an FSDS `USD` fact is admitted and carried as `USD/shares` (`numeric_policy.uom_matches` / `normalize_uom`). Grouping, `source_tags` provenance and the companyfacts lookup then use `USD/shares`.
  - Nothing else is mapped. A `USD` fact for a `shares` metric is still a mismatch, as is a foreign-currency EPS (`CAD` and the like), and both are quarantined.
  - The pre-review version of this bullet guessed that the lake had dropped the denominator. That guess was wrong: the convention comes from FSDS itself.

Contract 05 §6 gains `tolerance_abs`, `tolerance_basis`, `value_basis`, `latest_value`, `is_restated`, `value_kind`, `source_tags`, `resolution`, `compare_cik` and `period_end`, all with defaults (`eval/schemas.py` `NumericRow`).
**Consequences:** (draft by Claude for Shekar to review and rewrite)
- `eval/metrics.py` (Shekar's) must apply `max(tolerance_abs, tolerance_rel * |gold|)` instead of `tolerance_rel` alone; a diff is proposed in chat.
- The tolerance for a USD amount is 20x tighter than the runbook's 1% on large values, so the composer must keep full precision in `Claim.value`; rounding belongs in the text only.
- **Unit labels (2026-11-24).** `eval.metrics.normalize_value` reads the claim's unit label only and never infers a scale from magnitude, so an unlabelled or mislabelled value is scored against the gold unit as it stands. `Claim.unit` is optional in the `Answer` schema, so a correct answer given in millions or percent with no label would score wrong, biasing accuracy down unevenly across metrics. The contract is unchanged (no required field); instead the baseline composer prompt (`app/engine/baseline.py`, `VERSION` 0.2.0) makes `unit` mandatory on every numeric claim, from the fixed list `NUMERIC_UNITS`, and says `value` keeps every digit. A test that ties that list to `normalize_value` lands with `eval/metrics.py` (`tests/unit/eval/test_metrics.py`); until then the scoring behaviour described here is the intended definition, not a committed one. A missing or blank unit means the gold unit (no conversion). **The M5/M6 engine composer must follow the same rule**; if it cannot, make `unit` required for numeric claims in the schema (a contract change, section 4.3).
- **Self-describing results (2026-11-24).** The results `config` now records `sample`, `sample_seed` and `request_timeout_s` (data contracts section 6), so a seeded 30-question long-context run is distinguishable from a full run and reproducible. Without them only `n` differs between the two files.
- A metric that raises `ValueError` on a malformed row leaves that row unscored (`scoring_error`) and does not abort the run; more than 10% of a set's rows doing so fails the run (`eval/run.py`, exit 2), since an aggregate over the remainder would mislead.
- The second-source check matches companyfacts values exactly, for every unit, since companyfacts carries the filed value. The accession must match and, for the period, start and end dates may differ by up to 7 days (`DATE_SLACK_DAYS`): FSDS dates are month-end normalized, so a 52/53-week filer's real period ends a day or a few off (Sysco FY2023: 2023-07-01). Without that slack 48 of the first 240 draft rows were `unchecked`; with it 2 are. A difference of more than 7 days (Domino's Q2 2020: 14 days) stays `unchecked`, not forced to match. Tolerance is for answers, not for comparing two copies of one filing.
- Every results file records the corpus version it was scored against: a system that reads the corpus (`reads_corpus`) is stamped with `corpus_state.live_version`, read from the serving DB at run start, before any paid call. Retrieval goes through the `chunks` view, which follows that value, so an explicit `--corpus-version` that differs from it is refused rather than recorded. The first baseline run (`eval/results/2026-11-25T00-43-10Z_baseline-0.2.0_sonnet.json`) predates this and has `corpus_version: null`; its corpus version is NOT MEASURED for that run (the file does not say, and was not edited).
- The 300 rows still share their mapping with the engine, so they measure resolution and mapping, not ground truth. The hand-audited sanity set (50-100 questions from the filings themselves) is the independent check.
**How to revisit:** if the composer's rounding fails rows that a human would accept, widen `rel` for that unit with the evidence; never widen a tolerance after seeing a score.

## ADR-045: Paraphrase diversity from seeded style variants, not temperature (2026-11-23)
**Status:** proposed (drafted by Claude, pending Shekar)
**Context:** M04 §3.3 says to paraphrase with Haiku 5.5 at temperature 0.7. A non-default `temperature` returns 400 on Haiku/Sonnet 5.5 (the M4 docs check).
**Options considered:** (a) no paraphrase (rejected: template questions are too uniform for a router or planner). (b) several samples per question at the default temperature (rejected: costly and not reproducible). (c) one call per question with a style picked deterministically from six by a hash of (seed, row id) (chosen).
**Decision:** `make_numeric_set.py` (`STYLES`, `style_for`). A code guard rejects any paraphrase that loses the company (first word of the name, or the ticker), a fiscal year, the quarter, or "as originally reported" / "restated". The row then keeps its template text and is marked `paraphrased: false`, and the reason is logged.
**Consequences:** (draft by Claude for Shekar to review and rewrite) Diversity comes from the styles, not from sampling, so it is bounded by six styles. Paraphrases are reproducible from cassettes at $0. The guard catches dropped facts, not metric swaps ("profit" for "operating income"); that is what Shekar's 30-paraphrase check is for.
**How to revisit:** if the 30-row check finds metric drift, add a metric-synonym check to the guard using the catalog's `synonyms`.
