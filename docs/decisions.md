## ADR-001: Iceberg lake is the source of truth; Postgres is a rebuildable serving copy (2026-11-16)
**Status:** accepted
**Context:** Heavy batch processing (all XBRL facts since 2009, parsing and embedding about a million chunks) needs cheap storage and distributed compute. Interactive questions need tens-of-milliseconds lookups. Athena takes seconds and charges per scan.
**Options considered:** (a) everything in Postgres: simple, but no lake semantics and painful full rebuilds; (b) everything in the lake with Athena serving: too slow and pay-per-query; (c) lake for truth plus a versioned export loaded into Postgres: two systems, but each does what it's good at.
**Decision:** (c). Spark writes Iceberg; `export_serving` writes versioned Parquet; the loader builds `*_vN` tables and swaps views atomically.
**Consequences:** DRAFT (Claude; rewrite in your own words): Rebuilding Postgres from the lake is always possible, so the serving copy can be dropped, reloaded or re-versioned without data loss, and evals can pin a snapshot. The cost is two systems to operate, an export/load step that must stay idempotent, and a freshness lag equal to export plus swap time. Every serving table needs a version and a view swap, and nothing may write to Postgres as if it were authoritative.
**How to revisit:** if the serving subset outgrows one Postgres box, or the load and swap time exceeds the freshness target.

## ADR-002: Numbers come from a typed query plan compiled to SQL; the LLM never writes SQL on the main path (2026-11-16)
**Status:** accepted
**Context:** Free-form text-to-SQL is hard to verify and risky (wrong tags and periods, injection-shaped failures). The verifier needs to know exactly what a number means.
**Options considered:** (a) free-form text-to-SQL with guardrails; (b) an LLM-filled typed `QueryPlan` (enum-constrained metrics) + a deterministic compiler producing parameterized SQL and provenance expressions; (c) hard-coded intents only.
**Decision:** (b), with (a) as a guarded fallback behind a flag, measured separately.
**Consequences:** DRAFT (Claude; rewrite in your own words): The verifier can check each number against a plan and provenance expression, and the model's output space is constrained to enum metrics, which makes failures auditable and injection-shaped SQL off the main path. The cost is coverage: any metric, period rule or comparison the catalog and compiler don't express gets a refusal or falls to the guarded fallback, so the metric catalog and compiler become the bottleneck and need steady extension. The fallback must stay behind its flag and be reported separately in evals.
**How to revisit:** if plan coverage on real user questions stays below an acceptable level after extending the catalog.

## ADR-003: Apache Iceberg rather than plain Parquet for the lake (2026-11-16)
**Status:** accepted
**Context:** Restatements need upserts; evals must be reproducible against a past corpus; daily appends must be atomic.
**Options considered:** (a) plain Parquet + Glue partitions; (b) Iceberg; (c) Delta Lake.
**Decision:** Iceberg (Glue catalog support on AWS, EMR and Athena integration, MERGE, snapshots, time travel).
**Consequences:** DRAFT (Claude; rewrite in your own words): Restatements can be applied as MERGE upserts, daily appends are atomic, and evals can read a past snapshot via time travel. The cost is catalog and tooling friction (Glue catalog, EMR and Athena compatibility, local file-based catalog for dev) and table maintenance such as compaction and snapshot expiry. Spark, DuckDB and pyiceberg versions must stay compatible with each other.
**How to revisit:** if the tooling friction on EMR or Athena costs more than it saves.

## ADR-004: No Kafka in this project (2026-11-16)
**Status:** accepted
**Context:** Tracked companies file roughly tens to a few hundred 10-K/10-Qs per day in earnings season [estimate; replace with the M10 measurement]. Freshness target ≤ 24 h. One consumer.
**Options considered:** (a) Kafka/MSK streaming; (b) a daily scheduler + SQS fan-out with a DLQ.
**Decision:** (b). Streaming is shown in Project 2.
**Consequences:** DRAFT (Claude; rewrite in your own words): The design stays simple: one scheduler, SQS fan-out with a DLQ, and one consumer, which is cheap and easy to explain. The cost is no replayable event log and no sub-hour freshness, so reprocessing means re-running from the lake and the DLQ needs monitoring. If requirements change (many consumers, tighter freshness), this ADR has to be revisited, and the earnings-season volume estimate should be replaced with the M10 measurement.
**How to revisit:** sub-hour freshness requirements, many independent consumers, or a need for replayable event history.

## ADR-020: `fact_key` excludes the taxonomy year (2026-11-17)
**Status:** draft by Claude from the decisions on record (2026-11-17); Shekar to review and finalize the wording
**Context:** `fact_key` must group every reported version of one fact across filings, because `facts_history`, `n_versions`, `is_restated` and version selection all work per `fact_key`. A restatement changes the taxonomy year in `version` (`us-gaap/2022` in the original filing, `us-gaap/2023` in a later one). Measured on the 7 local quarters (`docs/milestones/M01-dq-report.md`, "Curated facts"): 8,229,693 `curated.facts` rows cover 8,053,335 distinct facts, 5,420,567 with one version, 1,795,462 with two, 181,400 restated. These counts are with the year stripped; they were not recomputed with the year in the key, so how many facts the year would have split is NOT MEASURED.
**Options considered:** (a) key over the full `version` string; (b) key over the year-stripped taxonomy family (`us-gaap`, `dei`, `custom`); (c) key over a normalized concept ID from a standard-taxonomy mapping.
**Decision:** (b). `fact_key = xxhash64(cik, tag, taxonomy, period_end, qtrs, uom)` with `taxonomy` the year-stripped family (`docs/plan/05_data_contracts.md` section 2.2). Including the year would put a fact and its own restatement under different keys, so `facts_history` would never group them and no restatement would be detected.
**Consequences:** A tag whose meaning changes between taxonomy years now shares a key across the years. Custom tags are keyed by `custom` plus the tag and CIK. The Spark and DuckDB twins must derive `taxonomy` identically; the differential test covers that. Option (c) is not built.
**How to revisit:** if a tag redefinition across taxonomy years shows up as a false restatement, move to (c) for the affected tags.

> Numbering note: ADR-005 is already reserved for "one EC2 box vs Lambda + Aurora" (`docs/plan/03_architecture_and_stack.md`, planned list above), so ADR-020 is numbered 020. Renumber if you prefer; the only other reference is the `taxonomy` bullet in `docs/plan/M01_xbrl_lakehouse.md` section 3.5.

## ADR-022: Deterministic ties and derived-Q4 eligibility and identity (2026-11-17)
**Status:** draft by Claude from the decisions on record (2026-11-17); Shekar to review and finalize the wording
**Context:** On 7 real quarters the Spark and DuckDB twins differed in 5,130 / 3,955 / 1,264 rows (`facts_history` / `facts` / `facts_dimensional`, both sides counted; `docs/milestones/M01-differential-analysis.json` at commit `f4daa7e`). By cause, summed over the tables: label-offset ties 9,792, fiscal-year ties 494 (+ 51 knock-ons), identity collisions 6. Two causes, both in the reference: (1) it broke ties (the label-offset mode, two FY rows of one filing after a fiscal-year change, 9M period-end groups) by list position, so its answer depended on input order; for three series it gave 2 different outputs over 60 random orders; (2) it derived Q4 from an FY row of any form, so a 10-Q's trailing-twelve-month value became a parent: 28,185 of 784,934 derived Q4 rows in the 7-quarter Spark `facts_history` came from forms other than 10-K, 10-K/A and 10-KT, and 175 `fact_id`s were shared by several rows, all involving a derived row.
**Options considered:** sort the reference's input vs give every `min`/`max` an explicit tie key vs leave ties undefined; restrict FY parents by form vs by whether the FY period end is a fiscal year end; put the 9M accession in the derived `fact_id` vs a flag column vs dropping derived rows from `facts_history`.
**Decision:** (1) Every input is sorted by (accession, value NULLs last, period end, quarters, cik, tag, taxonomy, uom) before any tie-sensitive step. The label-offset tie goes to the offset of the submission with the smallest accession; two FY rows go to the smaller value. These tie-breaks are stable, not business rules. (2) Derive Q4 only from an FY parent whose form is 10-K, 10-KT or 10-K/A, never from a 10-Q comparative. 20-F and 40-F are a deliberate scope exclusion, not an open question. (3) A derived Q4's `fact_id` is `xxhash64(fact_key, accession, nine_month_accession)`, so it cannot collide with a real fact. Rules 1 and 2 live in `pipelines/common/fiscal_ref.py` (applied by Shekar from `docs/proposals/ADR-022-fiscal_ref.diff`); rule 3 is in the twins and contract section 2.2.
**Consequences:** Derived Q4 rows in the 7-quarter Spark `facts_history` fell from 784,934 to 764,324, none from a non-annual form (was 28,185). 0 `fact_id`s are shared (was 175). Spark, DuckDB and the reference differ in 0 rows in all three tables on 2 and 7 quarters, with 0 unexplained differences; the reference run directly over 8,193 companies and 12,201,161 `facts_history` rows differs from DuckDB in 0 rows (2 quarters: 6,721 companies, 3,320,915 rows, 0). Q4 values that came from S-1s, 10-Qs, 20-Fs and 40-Fs no longer exist. Anything that stored a derived row's old `fact_id` must be rebuilt.
**How to revisit:** if Q4 from foreign annual reports or registration statements becomes a product requirement, widen the form set in `ANNUAL_FORMS`; if the tie rules matter to a real answer, replace them with a business rule.

## ADR-017: As-originally-reported vs restated values (2026-11-17)
**Status:** draft by Claude from the decisions on record (2026-11-17); Shekar to review and finalize the wording
**Context:** A company restates a figure in a later filing (a new 10-K, a 10-K/A, or the comparative column of the next year's report). Both values are in the data and finance users care which one an answer uses. Measured on the 7 local quarters (`docs/milestones/M01-dq-report.md`, "Curated facts"): 181,400 of 8,053,335 distinct facts are restated.
**Options considered:** (a) always the latest value; (b) always the original; (c) default to the as-originally-reported value, cite its native filing, and surface the restated value when the fact is restated.
**Decision:** (c). Answers default to the as-originally-reported value and cite the native filing, because that matches the cited document; when `is_restated` is true the restated value is surfaced next to it. `curated.facts` keeps both the latest and the original version per `fact_key` (one row when they have the same value, two otherwise); `facts_history` keeps every version (`docs/plan/05_data_contracts.md` section 2.2).
**Consequences:** The M4 gold set takes the original value for restated facts (`docs/plan/M04_eval_harness.md`). Answers about a restated fact carry two values and two citations.
**How to revisit:** if users ask for current values by default, flip the default and keep the same two columns.

## ADR-023: Filing fiscal labels reuse the fiscal_ref rules, so text and facts agree (2026-11-17)
**Status:** proposed
**Context:** `curated.filings` and `curated.chunks` need `fiscal_year` and `fiscal_period` (`docs/plan/05_data_contracts.md` section 2.2), and the engine joins text to numbers by those labels. `curated.facts` already labels facts with `fiscal_ref` (`y_end` plus a per-company label offset, M01 section 3.5 rules 1-4). A unit test asserts a filing's labels equal `derive_fiscal`'s labels for the same filing's facts.

## ADR-026: Title-only and cross-reference heading formats are scoped out of M2 (2026-11-17)
**Status:** proposed
**Context:** The section chain needs an `Item N` heading in the body. In the 150-filing sample (`docs/milestones/M02-blast-radius.json`) 13 filings still miss a required item after the two cheap fixes (14 before: `M02-blast-radius-before-fix.json`): financials 6 of 43 (7 before the Allstate fix), utilities 2 of 26, other 5 of 79; the 18 multi-registrant covers never fail. Causes (`summary.by_cause`): 11 only a TOC or index row, 5 mentioned only, 13 never written. Text before the first detected heading is not chunked: for the 11 filings missing Item 1 or 1A it is 8.1% to 29.8% of the document in nine, 100% for Citigroup, 1.0% for Synchrony (a complete filing: median 2.5%).
**Options considered:** (a) a title-based detector in M2: recovers some, risks false positives on the 138 working filings, unmeasurable without labels. (b) Scope out: these filings already parse `partial` or `no_sections`. (c) Chunk pre-heading text unlabeled: cheap, loses the section label.
**Decision:** (b). Title-only and cross-reference formats stay unsupported. Those filings' Item 1 and 1A text is NOT retrievable: it precedes the first detected heading and is not indexed (Citigroup: all of it). A missed later item is indexed under the previous section's label.
**Consequences:** (draft by Claude for Shekar to review and rewrite) In the 150-filing sample 13 filings (8.7%) still lack a required item, mostly financials (6 of 43) and utilities (2 of 26). For those filings the text before the first detected heading is not indexed (8.1% to 29.8% of the document in nine of them, 100% for Citigroup), and a missed later item is indexed under the previous item's label, so a section filter can return text with the wrong label or nothing. Nothing in the engine knows a filing is incomplete beyond its `partial` / `no_sections` parse status, so a question about one of these filings can be refused or answered from the wrong section, and that would look like a retrieval miss in the M4 eval. Stays unhandled: every filing whose items appear only in a table of contents, in prose, or under titles with no `Item N` text. What it buys: no title-based detector to maintain and no false-positive risk on the filings that parse `ok`. The prevalence in the full 500-company corpus is NOT MEASURED.
**How to revisit:** a later heading-detector improvement, not an M2 blocker; sooner if the M4 question-level eval misses on these filings.

## ADR-027: Spark jobs run on AWS Glue 5.0 because an Organization policy denies EMR Serverless (2026-11-20)
**Status:** proposed
**Context:** The account (`019593222039`) is a member of an AWS Organization, on the Free plan. A service control policy explicitly denies `emr-serverless:*` (`aws emr-serverless list-applications` returns an explicit deny in SCP `p-42ggg3sk`, 2026-11-20), so the application in M01 section 3.8 and ADR-024 cannot be created. Glue is on the Free-plan list (`04_aws_and_cost_plan.md` section 1) and its jobs are billed per DPU-second with a 1-minute minimum.
**Options considered:** (a) ask for the SCP to be lifted: outside my control and slow. (b) run Spark on the EC2 serving box: a second always-on cost and the box does not exist before M9. (c) Glue Spark jobs running the same modules: no new service, same Iceberg-on-Glue-catalog tables. A smoke run showed the Glue 5.0 runtime accepts `pipelines/` unchanged (including the `applyInPandas` path in `fiscal.py`) with no extra Python modules.
**Decision:** (c). `pipelines/common/spark_session.py` gains `env="glue"` (the `emr` Glue-catalog settings; the Iceberg jar comes from `--datalake-formats iceberg`). `pipelines/glue/*_job.py` are thin entry points over the unchanged `pipelines.spark` jobs; `scripts/glue_deploy.sh` publishes them and `pipelines.zip` to `s3://<lake>/scripts` and `artifacts/glue`. `infra/terraform/modules/glue` defines `edgarqa-fsds-to-iceberg` and `edgarqa-normalize-facts` (G.1X, 4 workers, 30 minute timeout, no retries). The EMR entry points, module and image stay in the repo, disabled (`create_emr_application = false`). `fsds_to_iceberg` now reads `s3://` sources, and both jobs take a subset (`--ciks`, `--fiscal-years`, `--limit-filings`) that smoke runs write to `raw_smoke` / `curated_smoke`, never to `raw` / `curated`.
**Consequences:** (draft by Claude for Shekar to review and rewrite) Glue is the only Spark runtime until the Organization policy changes: the EMR entry points, module and image stay in the repo disabled, which is code to keep consistent but never run. Code under `pipelines/spark` must run on the Glue 5.0 runtime (Python 3.11) as well as locally (Python 3.12), and the parser jobs install their PyPI dependencies at job start with `--additional-python-modules`. Deploying is a manual step (`make glue-deploy`, a dry run unless `YES=1`), so the code on S3 can lag the repository (it did after the Berkshire parser fix). Jobs bill per DPU-second with a one-minute minimum and no idle cost, and the measured cost of each run is in `docs/milestones/job-metrics/*.json`. ## ADR-028: JPMorgan 10-Qs have no Item 1 or Item 2 headings, so Part I is not indexed by section (2026-11-20)
**Status:** proposed
**Context:** All 21 JPMorgan Chase & Co. 10-Qs in the local set (CIK 19617, filed 2020-05-07 to 2026-11-03; `docs/milestones/M02-parse-metrics.json` `html.non_ok`) parse `partial` with `missing sections: P1-1, P1-2`. Their Part I is a cross-reference format: `Item 1. Financial Statements` and `Item 2. Management's Discussion and Analysis` appear only as rows of one table of contents with page numbers, and the body has no such headings (it has `Item 3`, `Item 4` and the whole of Part II). Measured by re-running the parser on the stored filings (2026-11-20; the figures are shares of each filing's extracted text): in the 6 filings from 2020-05-07 to 2021-11-02, 42.5% to 45.2% (263,552 to 335,563 characters) comes before the first detected heading and is **not chunked, so it is not in `curated.chunks` at all**, and a further 53.2% to 55.8% sits under `P2-1A` (Risk Factors); in the 15 filings from 2022-05-03 to 2026-11-03, 98.7% to 99.2% (560,652 to 733,882 characters) sits under `P2-6` (Exhibits). The cause of that last label is the heading chain: the table of contents is one table whose last row (`P2-6`) is followed by the whole document, so the chain that maximises text weight is that single row. The 6 JPMorgan 10-Ks parse `ok` but 83.4% to 85.1% of their text sits under Item `15` for the same cross-reference reason (ADR-026 covers 10-Ks). Facts are unaffected: they come from XBRL, not from this text.
**Options considered:** (a) down-weight table-of-contents rows (several item headings in one table block) in `detect_sections`: it removes the `P2-6` label, but with no `Item 1` or `Item 2` heading to take its place the body would then precede the first detected heading and be unchunked (reasoned from the heading positions above, NOT tested), and it touches the heading chain every other filing goes through. (b) a title-based detector for JPMorgan's own page titles ("Consolidated Financial Statements", "Management's discussion and analysis"): the right fix, but it needs gold labels to avoid false positives on the 114 filings that parse `ok`, which is parser work and not a heading tweak. (c) accept the limitation and record it.
**Decision:** (c). No parser change for this format. Stated plainly: for the 21 JPMorgan 10-Qs, Part I (the financial statements and the MD&A) **cannot be retrieved by section**; for the 6 filings of 2020 and 2021 about 43% to 45% of the text **is not indexed at all**, and for the other 15 the text is indexed but under the wrong label (`P2-6`), so a section filter for Items 1 or 2 returns nothing and one for Item 6 returns the whole filing. Other banks or filers that use the same cross-reference format are NOT MEASURED: only 5 of the 500 tracked CIKs are fetched, so the share of the corpus affected is unknown.
**Consequences:** (draft by Claude for Shekar to review and rewrite) The 21 JPMorgan 10-Qs in the local set stay `partial`: 15.6% of the 135 local filings, which is why strict parse success is 84.4% and misses the 95% target. For those filings Part I (the financial statements and the MD&A) cannot be retrieved by section, 42.5% to 45.2% of the text of the six 2020-2021 filings is not in `curated.chunks` at all, and in the other 15 the text sits under `P2-6`. Numbers from XBRL facts are not affected, since they do not come from the parsed text; only text questions about JPMorgan's quarterly MD&A and notes are. Any other filer with the same cross-reference format is NOT MEASURED, so the corpus-wide share is unknown until the full parse. Nothing is done about it now: no title-based detector to build or test, at the price of an open known hole in the text index.
**How to revisit:** after the full corpus is parsed, count filings whose `P1-1` or `P1-2` is missing and group them by CIK; if JPMorgan-like filers are more than a handful, or the M4 question-level eval misses on them, build the title-based detector (b) with hand labels for these filings first.

**Update (2026-11-21), revisit trigger fired:** the full-corpus parse counted the 10-Qs missing both `P1-1` and `P1-2` by company: **1,226 filings in 78 of the 500 companies**, not 21 filings in one (`docs/milestones/M02-fullcorpus-metrics.json`, `cross_reference_10q_both_p1_missing`). Most of that was a different defect, the 10-Q part state (ADR-031), and after ADR-031 **755 filings in 60 companies** are still missing both. Of the 1,135 10-Qs still `partial`, **554 have no body heading for the missing item** (the format this ADR describes; JPMorgan and Colgate are 21 of 21 each and unchanged) and 581 have a heading that the chain did not choose (`docs/milestones/M02-residual-causes.json`). Decision (c) stands for the no-body-heading format; its cost is now measured: 554 filings.

## ADR-029: "Item 1.A." (a dot before the letter) is read as item 1A (2026-11-20)
**Status:** proposed
**Context:** Rollins writes its headings as `Item 1.A.`, `Item 1.B.`, `Item 7.A.`. `sections._ITEM` read `Item 1.A. Risk Factors` as item 1 with the title `A. Risk Factors`, so the filing's Item 1 first chunk was the risk-factor text and 1A was "section not found" (accession `0001171200-21-000076`, Rollins 10-K FY2020; section-gold rows ROL 1 and ROL 1A; 45/50 and then 47/50 in `docs/milestones/M02-sections-eval.json`). The labeling harness's own candidate regex does not list dotted headings either, so ROL 1A needed a manual label.
**Options considered:** (a) allow a dot before any letter: also reads "Item 1. A new risk factor ..." (the article "A") as item 1A. (b) allow the dot only when the letter is itself followed by a dot (`Item 1.A.`): narrow. (c) also allow `Item 1.A` with no trailing dot: wider, with the article-"A" risk of (a).
**Decision:** (b), in `pipelines/parsing/sections.py` and in the noise filter's copy of the regex in `html_blocks.py`. Tested on the 150 cached S&P 500 10-Ks and the 135 local filings: only Rollins changed (it gains 1A and 1B and its Item 1 starts at its own heading). Tests: synthetic headings and a dotted TOC in `tests/unit/parsing/test_sections.py`, and the real filing in `tests/unit/parsing/test_rollins_dotted_item_regression.py` (skipped without the blast cache); they fail without the fix.
**Consequences:** (draft by Claude for Shekar to review and rewrite) Rollins' 10-Ks are indexed under the right items, and the section-gold score rises from 47/50 to 49/50 (98.0%) because the parser improved, with the gold set unchanged. Across the 150 cached and 135 local filings only Rollins changed, so the dotted form looks rare, but only those two sets were tested. Stays unhandled: `Item 1.A` without the trailing dot and any other spelling not in the tests. The heading regex now lives in three places (`sections.py`, `html_blocks.py`, and `eval/labeling_harness.py`, which must not import the parser), and they can drift apart. A fresh gold template would still need the harness regex changed to list dotted headings.
**How to revisit:** if the full-corpus parse finds filings missing 1A or 1B with a dotted or otherwise unusual item spelling, widen the pattern (c) with a regression test for each new spelling.

## ADR-030: NiSource's Item 7 starts at its "(continued)" page header, so the start of its MD&A is indexed under Item 6 (2026-11-20)
**Status:** proposed
**Context:** NiSource 10-K FY2024 (`0001111711-25-000008`) repeats the Item 7 heading at the top of each MD&A page, and from the second page adds `(continued)`. `detect_sections` picks the `ITEM 7. ... (continued)` copy (block 497) as the Item 7 heading, not the real heading (block 486). Item 6's section therefore runs from block 484 to 497 and holds the real Item 7 heading, the `Index | Page` table and the start of the executive summary, about 4,700 characters of the plain-text rendering (offsets 151,565 to 156,292). The first Item 7 chunk starts at the `(continued)` page (section-gold row NI 7, a miss in `docs/milestones/M02-sections-eval.json`). Item 8 has the same pattern (heading block 691 is the `(continued)` copy) but the gold anchor sits after the skipped index, so the evaluator scores it correct. The cause is NOT verified: one possibility is that the `Index | Page` table after the real heading looks like a table of contents to the candidate scoring.
**Options considered:** (a) rework the candidate scoring so the first copy of a repeated heading wins over its `(continued)` variants: touches the chain every filing goes through, and needs measuring on the 285 cached and local filings plus labels. (b) treat `(continued)` as part of a heading's repeat key in the noise filter: smaller, NOT tested. (c) accept the limitation and record it.
**Decision:** (c). No parser change for this format. Affected filing: the NiSource 10-K above (Item 7 start; Item 8 start by the same pattern). Other filers that use `(continued)` page headers are NOT MEASURED.
**Consequences:** (draft by Claude for Shekar to review and rewrite) For this filing the first ~4,700 characters of the MD&A (its page index and the opening of the executive summary) are stored under Item 6 ("Reserved"), so an Item 7 filter misses them and an Item 6 filter returns MD&A text. The rest of Item 7 is correct. The section-gold result keeps this miss as a genuine parser error (49/50 = 98.0%) and the evaluator would not show a boundary that is late but lands on matching text, as in NI 8. How many corpus filings share the pattern is unknown until the full parse. What it buys: no change to the heading chain while the other filings tested are stable.
**How to revisit:** after the full-corpus parse, count filings whose chosen heading text ends in `(continued)`; if more than a handful, or the M4 eval misses on them, try (b) first, then (a), each with a before/after chunk diff over all cached filings.

## ADR-031: A contents table no longer moves the 10-Q part, and a missing Item 1 heading is implied (2026-11-21)
**Status:** proposed
**Context:** The full-corpus parse (13,239 filings, `docs/milestones/M02-fullcorpus-metrics.json`) left 11,178 filings `ok`, 84.4% strict against a 95% target, and 1,226 10-Qs in 78 of 500 companies missing both `P1-1` and `P1-2`. ADR-028 had attributed that symptom to JPMorgan's cross-reference format. Reading the parser on two affected filings (Humana `0000049071-26-000066`, Moderna `0001682852-26-000197`) showed two other defects. (1) `_candidates` takes the current part from `Part I` / `Part II` lines; a contents table that names both leaves the part at II, and the body's `Item 1.` / `Item 2.` (which carry no Part) were coded `P2-*` (Moderna's financial statements sat under `P2-1`, Legal Proceedings) or, before any Part line, dropped. (2) Some 10-Qs print no `Item 1` heading in the body: the financial statements follow the contents table, so the first heading is `P1-2` and the text before it is never chunked (Corning `0000024741-26-000279`).
**Options considered:** (a) scope the part to a contents table, read an item as Part I until a Part line says otherwise, and imply `P1-1` after the contents table (chosen). (b) The title-based detector of ADR-028(b): the larger piece of work, and it needs gold labels. (c) Keep the old chain whenever the new one covers less text: leaves the bug in place as a fallback. (d) Fix (1) only: tested first and rejected, because 40 of the affected filings (11 CIKs) then lost about 48% of their text from the index (their old result put everything under a contents-table `P2-6`, wrong but retrievable; the new one found `P1-2` and later but left the financial statements before the first heading).
**Decision:** (a), in `pipelines/parsing/sections.py`: a table block that names two or more different Parts keeps its part to itself (`_is_contents_table`); before any Part line a 10-Q item is Part I; and `_imply_part1` starts `P1-1` at the block after the contents table (the first run of candidates at most `TOC_GAP_BLOCKS` = 20 blocks apart) when the first chosen section is `P1-2` or later and at least `MIN_IMPLIED_CHARS` = 5,000 characters lie between. The implied section has an empty `heading_text`, no anchor, and the canonical title. Both constants are judgement, not fitted: in the 486 filings where `P1-1` was implied the smallest was 5,693 characters, so the 5,000 guard never fired on the evidence; it is covered by a unit test (`tests/unit/parsing/test_part_state.py`, mutation-checked). 10-Ks are untouched. **This is the last parser fix for M2.**
**Verification (before any cloud run):** `eval/parser_diff.py` ran the committed and the patched detector over 2,661 stored filings (`docs/milestones/M02-part-state-diff.json`): the 1,226 affected 10-Qs, 1,000 seeded previously-`ok` 10-Qs, 150 `partial` 10-Qs missing one item, 150 blast-radius 10-Ks and the 135 local filings. Previously-`ok` filings changed: **0**. **Gate relaxation, recorded as such:** the gate as first worded was "no filing loses block coverage". It failed literally: 417 changed filings lost block coverage (66,245 characters in total, at most 0.53% of a filing). Every one of those blocks is a heading or title line of a heading that is now recognised (1,702 heading blocks, 65,615 characters, longest 113; plus 630 characters of second-line titles in 9 filings): the old parser had left `Item 1. Legal Proceedings`, `Item 1A. Risk Factors` and similar inside a mislabelled body, and a section's own heading is never part of its body, so its text now lives in `section_title`. Shekar approved replacing the gate with "no filing loses BODY text": **0 body characters lost, 23,191,035 gained**. The strict wording is kept in this ADR so the change is visible.
**Result on the full corpus** (`docs/milestones/M02-adr031-reparse.json`, from `curated.filings` before and after; code `6f528ea82a1a`): strict parse success **84.43% to 88.53%** (11,178 to 11,720 `ok` of 13,239; `ok` + `partial` 99.06%), still **below the 95% target**. 542 filings went `partial` to `ok` and 1 went `no_sections` to `partial`; **0 downgrades, 0 previously-`ok` filings changed in status, sections or chunks, 0 changed 10-K or FinanceBench rows**. Of the 1,226 10-Qs missing both items, 421 are now `ok` and 755 still miss both. Of the 78 companies, 36 have at least one filing recovered, 14 have every affected filing recovered and 60 still have a filing missing both. **Residual** (1,135 10-Qs `partial`, 83 companies; `docs/milestones/M02-residual-causes.json`, parser-level: a missing item has a "body heading" when a candidate for it has at least 3,000 characters of text after it): **554 no body heading** (the ADR-028 format: JPMorgan and Colgate are 21 of 21 filings each and unchanged; 37 companies have no other kind) and **581 a body heading that the chain did not choose**, of which 409 are a chain that is a single contents-table row (`P2-6`): the last row of a contents table is weighted by all the text up to the next candidate, so one row outweighs the body chain (ADR-028 option (a)); Humana (21 of 21), Delta (18 of 21) and Netflix (10 of 21) are in this class. The other 172 are chains where a neighbouring heading conflicts. 125 filings are `no_sections` and 259 10-K and 10-K/A filings are `partial` (not touched; causes NOT MEASURED).
**Consequences:** (draft by Claude for Shekar to review and rewrite) 542 filings that were `partial` are `ok`, and the financial statements of the 10-Qs without an `Item 1` heading are indexed under `P1-1` instead of being dropped or labelled `P2-6`. M2's parse-success target is missed (88.5% against 95%); the 1,135 residual 10-Qs, 8.6% of the 13,239 filings, stay `partial`, so a Part I section filter returns nothing for them, and the other half of them (581) is a heading the parser saw and lost, which a later fix could recover without new labels. The implied `P1-1` also swallows whatever sits between the contents table and `Item 2` (a forward-looking-statements page, a glossary) under the label `P1-1`. Rolling it out found a separate bug: the first re-parse timed out in `merge_curated`'s `chunk_id NOT IN (subquery)` delete and left 51,523 stale chunks (old section labels) in 440 filings; the delete is now an anti-join `MERGE` and the final re-parse left `curated.chunks` equal to `curated.filings.n_chunks` with 0 orphans (`docs/milestones/M02-report.md`). The heading regex still lives in three places (ADR-029); the part logic lives only in `sections.py`.
**How to revisit:** do not add a third format fix inside M2. After M2, try in this order, each measured with `eval/parser_diff.py` on the same 2,661 filings plus the 1,135 residual: (i) weight a contents-table row as zero so a single-row chain cannot win (addresses the 409); (ii) look at the other 172; (iii) the title-based detector for the 554 (ADR-028(b)), with hand labels.
