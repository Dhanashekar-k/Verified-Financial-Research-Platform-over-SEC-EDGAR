## Stage D: retrieval benchmark (latency PRELIMINARY)

200 deterministic queries per set (spans of chunks, and two unrelated spans joined, the harder case); instance m7i-flex.large; server 17.12 (Debian 17.12-1.pgdg12+1), pgvector 0.8.7, 1,081,461 chunks. Truth is exact search over the same `halfvec(384)` column with index scans off (1.21 s per query). Recall is the share of the exact top-10 that the index returns; the headline is the lower of the two sets; CIs are 10,000-resample bootstrap intervals.

**Chosen default `ef_search` = 800.** 800 is the smallest tested ef_search whose recall@10 on the harder query set reaches 0.95 (0.9615; its 95% CI [0.942, 0.978] still includes values below 0.95); dense search there takes p50 21.8 ms, p95 30.7 ms on a Free-plan flex instance (preliminary). Lower settings are cheaper but miss the gate: ef 40: 0.732, ef 100: 0.842, ef 200: 0.892, ef 400: 0.924.

**Outcome against the DoD:** recall@10 reaches 0.95 only from ef_search 800 (and the interval still reaches below 0.95); at ef_search <= 200 it is well short. This is documented, not hidden. Whether it matters is an M4 question, to be answered by retrieval quality against FinanceBench gold (ADR-040).

### Numeric lookup and hybrid search (PRELIMINARY)

Numeric lookup (200 lookups): p50 1.3 ms, p95 1.7 ms (target p95 < 50 ms).

Hybrid = full-text (`and` mode) + dense + RRF + embedding the question on the box, no rerank; 100 questions per setting.

| ef_search | total p50 | total p95 | embed p50 | lexical p50 | lexical p95 | dense p50 | dense p95 | fuse p50 |
|---|---|---|---|---|---|---|---|---|
| 200 | 433.6 ms | 1572.9 ms | 15.8 ms | 32.4 ms | 1345.2 ms | 313.3 ms | 817.3 ms | 0.0 ms |
| 800 | 238.6 ms | 1018.7 ms | 15.5 ms | 33.2 ms | 797.5 ms | 149.9 ms | 476.9 ms | 0.0 ms |

**Known cost, not fixed in M3:** the hybrid target is missed at every setting, and the tail is the full-text leg (lexical p95 above): `ts_rank_cd` ranks every row that matches. The first run used an OR query of the same words, a stress shape, and its lexical p50 was 4700.7 ms. Separately, the dense leg inside the hybrid run is much slower than the standalone dense search at the same ef_search (compare the two tables). My suspicion is that the full-text queries evict HNSW pages from the 8 GiB page cache (the box measured a dense p50 of 6.5 ms standalone vs about 300 ms after heavy lexical work), but I did not isolate it.

BGE query instruction A/B (reported, not used to choose; ADR-033): source chunk in the exact top-10 with the instruction 0.110 vs without 0.095; MRR@10 0.0323 vs 0.0301; top-10 overlap between the variants 0.589. Caveat from the bench: queries are spans of the chunks themselves; this favours no instruction (ADR-033). The queries are chunk spans, not questions, so this says little; the default stays as ADR-033 decided until M4 compares them on the gold sets.

Filtered dense search: 50 single-company queries; queries returning fewer than 10 rows: 0 with the default scan limit and 0 with `hnsw.max_scan_tuples` = 500,000. The planner used the HNSW index in 2 of 10 sampled plans; otherwise it prefers the (cik, fiscal_year) B-tree. Note from the bench: when the planner prefers the (cik, fiscal_year) btree the HNSW iterative scan is not exercised for that query.

CPU steal over the final bench: 0.0017% of all time, 0.0021% of busy time. No throttling showed in the sampler, but flex can still throttle under other conditions, so every latency here stays PRELIMINARY until M9.
